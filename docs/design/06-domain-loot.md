# 06 -- Loot Priority Signups

> Domain directory: `functions/loot/` (6 files)
> Command file: `commands/loot.js`
> Keyv namespace: `lootResponses`
> Service dependency: `services/raiderioService.js` (static raid data)
> Scheduled tasks: none (triggered by command only)

---

## Overview

The loot system lets raiders declare their interest level for boss loot drops in the current raid tier. Each boss in the active raid gets a Discord embed with four priority buttons. Raiders click a button to register their preference; clicking a different button moves them automatically. Loot posts are auto-generated by scanning Raider.io static data for the current raid tier, starting from expansion 9 and walking forward.

## Auto-Discovery Algorithm

**Function:** `checkRaidExpansions(client)` in `checkRaidExpansions.js`

**Trigger:** `/loot create_posts` slash command (manual only, no scheduled task).

**Steps:**

1. Set `initialExpansion = 9` and `currentExpansion = initialExpansion`.
2. Enter a `while (!complete)` loop:
   a. Call `getRaidStaticData(currentExpansion)` from `raiderioService`.
   b. **If the API returns status 400** (`raidStaticDataResponse?.response?.status === 400`): set `complete = true` -- no more expansions exist.
   c. **If the response contains `raids`**: sort and scan for the current raid (see below).
   d. Increment `currentExpansion++` and continue.
3. The loop terminates either when a 400 is hit or the current raid is found.

**Raid Sorting:**

```js
raidStaticDataResponse.raids.sort((a, b) => {
    if (new Date(a.ends.eu) > currentDate) return 1;
    return a.ends.eu > b.ends.eu ? 1 : -1;
});
```

This places future raids (where `ends.eu > now`) after past raids, then sorts by end date ascending. The effect is that past raids come first sorted chronologically, followed by future/current raids.

**Current Raid Detection:**

Iterates sorted raids with `for await...of`. The first raid where `new Date(raid.ends.eu) > currentDate` is treated as the active raid. For each encounter in that raid:

```js
await addLootPost(channel, {
    id: encounter.id,
    name: encounter.name,
    url: `https://www.wowhead.com/npc=${encounter.id}`,
});
```

Posts are sent to the channel identified by `lootChannelId` from `config.json`. After processing the first current raid, `complete = true` and the outer loop exits via `break`.

## Loot Post Structure

**Function:** `generateLootPost(bossName, bossId, playerResponses)` in `generateLootPost.js`

Returns `{ embeds: [embed], components: [row] }`.

### Embed

| Property | Value |
|----------|-------|
| Title | `bossName` (the encounter name from Raider.io) |
| Timestamp | `setTimestamp()` (auto-set to current time) |
| Fields | 4 inline fields (see below) |

**Fields:**

| Name | Value Source | Inline |
|------|-------------|--------|
| `'Major'` | `playerResponses.major` | `true` |
| `'Minor'` | `playerResponses.minor` | `true` |
| `'Want In'` | `playerResponses.wantIn` | `true` |
| `'Do not need'` | `playerResponses.wantOut` | `true` |

Each field value is either `'*None*'` (initial state) or a newline-separated list of raider character names.

### Buttons

One `ActionRowBuilder` with 4 buttons:

| CustomId | Label | Style | Meaning |
|----------|-------|-------|---------|
| `updateLootResponse\|major\|${bossId}` | `'Major'` | `ButtonStyle.Success` (green) | Major upgrade for the raider |
| `updateLootResponse\|minor\|${bossId}` | `'Minor'` | `ButtonStyle.Primary` (blurple) | Minor upgrade |
| `updateLootResponse\|wantIn\|${bossId}` | `'Want In'` | `ButtonStyle.Secondary` (grey) | Would like to be included |
| `updateLootResponse\|wantOut\|${bossId}` | `'Do not need'` | `ButtonStyle.Danger` (red) | Does not need the loot |

**CustomId format:** Three segments separated by pipe (`|`) characters:
- Segment 0: action identifier `updateLootResponse`
- Segment 1: response type (`major`, `minor`, `wantIn`, `wantOut`)
- Segment 2: boss ID (integer from Raider.io encounter data)

## Data Shape (lootResponses Namespace)

**Key:** Boss ID as a string (e.g., `"12345"`)

**Value:**

```json
{
    "major": ["userId1", "userId2"],
    "minor": ["userId3"],
    "wantIn": [],
    "wantOut": ["userId4"],
    "channelId": "Discord channel ID where the post lives",
    "messageId": "Discord message ID of the embed",
    "bossName": "Encounter name from Raider.io",
    "bossUrl": "https://www.wowhead.com/npc={encounterId}"
}
```

- The four arrays (`major`, `minor`, `wantIn`, `wantOut`) contain Discord user IDs (strings).
- `channelId` and `messageId` are stored to locate the Discord message for edits/deletes.
- `bossName` and `bossUrl` are stored for re-rendering.

**Initial state** (set by `addLootPost`): All four arrays are empty `[]`.

## Adding a Loot Post

**Function:** `addLootPost(channel, boss)` in `addLootPost.js`

**Parameters:**
- `channel` -- Discord channel object (fetched from `lootChannelId`)
- `boss` -- Object with `{ id, name, url }`

**Steps:**

1. Build initial `playerResponses` with all fields set to `'*None*'`:
   ```js
   const playerResponses = {
       major: '*None*',
       minor: '*None*',
       wantIn: '*None*',
       wantOut: '*None*',
   };
   ```
2. Call `generateLootPost(boss.name, boss.id, playerResponses)` to build the embed+buttons.
3. Send the message to the channel: `const message = await channel.send(messageObject)`.
4. Persist to the database:
   ```js
   const bossLootResponse = {
       major: [],
       minor: [],
       wantIn: [],
       wantOut: [],
       channelId: channel.id,
       messageId: message.id,
       bossName: boss.name,
       bossUrl: boss.url,
   };
   await lootResponses.set(boss.id, bossLootResponse);
   ```

**Database instance:** `new Keyv(databaseString, { namespace: 'lootResponses' })` -- no error handler registered in this file.

## Response Update Flow

### Button Click Routing (interactionCreate.js)

When a button is clicked:

1. `interaction.customId.startsWith('updateLootResponse')` matches.
2. The customId is split: `const [, response, bossId] = interaction.customId.split('|')`.
3. **Raider validation:** The handler fetches all raiders from the `raiders` namespace and looks up the clicking user's Discord ID. If no match is found:
   ```js
   await interaction.reply({
       content: `<@${interaction.user.id}> Could not find a character name linked with your discord id. Please contact an officer!`,
       ephemeral: true,
   });
   ```
   Note: execution continues past this point (no early return), so `updateLootResponse` is still called and `interaction.update()` is attempted. This is a potential bug -- the ephemeral reply and the update may conflict.
4. Calls `updateLootResponse(client, response, bossId, interaction.user.id)`.
5. The return value is passed to `interaction.update()`.

### Core Logic (updateLootResponse.js)

**Function:** `updateLootResponse(client, response, bossId, userId)`

**Steps:**

1. Fetch current boss data: `let bossLootResponses = await lootResponses.get(bossId)`.
2. **Remove user from ALL response arrays** (ensures a user can only be in one category):
   ```js
   const removeFromAllLootResponses = (bossLootResponses, userId) => {
       const result = bossLootResponses;
       result.major = bossLootResponses.major.filter((r) => r !== userId);
       result.minor = bossLootResponses.minor.filter((r) => r !== userId);
       result.wantIn = bossLootResponses.wantIn.filter((r) => r !== userId);
       result.wantOut = bossLootResponses.wantOut.filter((r) => r !== userId);
       return result;
   };
   ```
3. **Add user to the specified response type:** `bossLootResponses[response].push(userId)`.
4. Persist: `await lootResponses.set(bossId, bossLootResponses)`.
5. Refresh the Discord message: `await updateLootPost(client, bossId)`.
6. Returns `''` (empty string, used as the update content).

### Post Re-rendering (updateLootPost.js)

**Function:** `updateLootPost(client, bossId)`

**Steps:**

1. Fetch boss data from DB: `const bossLootResponses = await lootResponses.get(bossId)`.
2. Fetch all raiders from the `raiders` namespace into an array of `{ key: characterName, value: userId }` objects.
3. For each response type (`major`, `minor`, `wantIn`, `wantOut`), call `generatePlayerResponseString(userIdArray, raidersObject)`.
4. Generate the updated embed+buttons via `generateLootPost(bossName, bossId, playerResponses)`.
5. Fetch the Discord channel and message using stored `channelId` and `messageId`, then `message.edit(messageObject)`.

**Player Response String Generation:**

```js
const generatePlayerResponseString = async (playersId, raidersObject) => {
    let result = '';
    for (const playerId of playersId) {
        const raiderObject = raidersObject.find((o) => o.value === playerId);
        if (raiderObject) {
            result += `${raiderObject.key}\n`;
        }
    }
    return playersId.length && result.length ? result : '*None*';
};
```

- Resolves Discord user IDs to character names by searching the raiders namespace.
- If a user ID is in the array but not found in raiders, they are silently skipped.
- Returns `'*None*'` if the array is empty or no names resolved.

**Database instances in updateLootPost.js:** Two Keyv instances:
- `lootResponses` with namespace `'lootResponses'` (with error handler)
- `raiders` with namespace `'raiders'` (with error handler)

## Deleting Loot Posts

**Function:** `deleteLootPost(client, bossId)` in `deleteLootPost.js`

**Steps:**

1. Fetch boss data: `const bossLootResponses = await lootResponses.get(bossId)`.
2. If not found: `throw 'Cannot find boss loot'`.
3. Fetch the Discord channel, fetch the message, delete it.
4. Remove from database: `await lootResponses.delete(bossId)`.

## Slash Command Interface

**Command:** `/loot` with 5 subcommands (defined in `commands/loot.js`)

| Subcommand | Parameters | Behavior |
|------------|-----------|----------|
| `add_post` | none | Creates a test post with `id: 1`, `name: 'Test Boss'`, `url: 'http://www.google.com'` in the current channel. Replies ephemeral `'Post added'`. |
| `delete_post` | `boss_id` (integer, required) | Deletes a single loot post. Replies ephemeral `'Loot post removed'`. |
| `delete_posts` | `boss_ids` (string, required) | Comma-separated boss IDs. Splits on `,`, creates `deleteLootPost` promises in array, replies `'Deleting posts'`, then `Promise.all()` and edits reply to `'Deleted posts'`. |
| `create_posts` | none | Calls `checkRaidExpansions(interaction.client)` for auto-discovery. Replies `'Checking raid expansions'`, edits to `'Checked raid expansions'` on completion. |
| `update_priority_post` | `create_post` (boolean, optional) | If `create_post` is true, calls `createPriorityRankingPost(interaction)`. Otherwise calls `updatePriorityRankingPost(interaction.client, interaction)`. Replies with creating/updating status. |

**Bug:** The `create_posts` subcommand uses `else if` but `update_priority_post` uses `if` (not `else if`). This means if the subcommand is `update_priority_post`, it will also be checked after `create_posts` runs. In practice this doesn't cause issues because `getSubcommand()` returns a single value, but the `update_priority_post` handler will always execute if matched, even after `create_posts` completes.

**Note:** The `update_priority_post` subcommand is part of the `/loot` command but actually delegates to EPGP functions (`createPriorityRankingPost`, `updatePriorityRankingPost` from `functions/epgp/priorityRankingPost.js`). See [07-domain-epgp.md](07-domain-epgp.md) for details.

## Raider.io Integration

The loot domain uses a single Raider.io endpoint:

**`getRaidStaticData(expansion_id)`** from `services/raiderioService.js`:
- URL: `https://raider.io/api/v1/raiding/static-data?expansion_id=${expansion_id}`
- No authentication required.
- Returns an object with a `raids` array. Each raid has:
  - `name` (string): Raid name
  - `slug` (string): URL-safe identifier
  - `ends.eu` (string/null): ISO date when the tier ends in EU region, `null` if ongoing
  - `encounters` (array): Each encounter has `id` (integer) and `name` (string)
- Error pattern: `.catch((error) => error)` -- returns the error object as a resolved value. The caller checks `raidStaticDataResponse?.response?.status === 400` to detect end of expansions.
